§1Three Architectural Layers

O sistema pós-pivot é dividido em três camadas que se comunicam por contratos tipados (Pydantic v2) e contratos de fronteira (UEID 4-part, JSON-RPC sobre stdio). Cada camada é autônoma; vazamento entre elas é tratado como bug.

Os seis saltos onde pode quebrar:

  1. CLI/TUI input — shell parsing (Windows quirks), typer args
  2. Agent Harness — Python imports, sys_ikigai path, OTel SDK
  3. v2 LangGraph — node wiring, OTel instrumentation
  4. MCP Server subprocess — stdio JSON-RPC handshake, PYTHONPATH, cwd shadow bug
  5. Tool handler — Pydantic validation, queue enqueue, action rejection (-32601)
  6. Mesh consumer worker — currently offline, so events never propagate to forks

§5Root Causes · Why Nothing End-to-End Works

O harness nunca foi exercitado como sistema completo. Cada smoke test isolado passou, mas a integração revela falhas estruturais que não são fix-by-tweak:

Structural Blockers (need fixing, not tweaking)

  • OTel version conflict in pyproject.toml — opentelemetry-instrumentation-langchain>=0.42b0,<0.43 vs. opentelemetry-instrumentation-logging>=0.48b0,<0.49. uv sync fails outright. The --no-deps workaround broke OTel observability → cascades into harness crash on import.
  • src/ikigai/src/ikigai/ doesn't exist — package was renamed to sys_ikigai/ in commit 685dec5, but pyproject.toml still references include = "ikigai" in packages. Build fails on poetry, editable install skips the package.
  • PYTHONPATH wrong in ikigai.bat — assumes src/ikigai/.venv local; worktree layout has .venv at worktree root. Even after fixing, the bat doesn't include worktree root in PYTHONPATH so from sys_ikigai.X fails.
  • Mesh consumer worker offline by default — no systemd / cron / daemon. Events pile up in data/review_queue/ and never propagate to fork slices. mesh-show always returns null except for CLI.
  • No integration tests — drift net (44/44 PASS) covers unit-level contracts only. No test exercises the path user input → dcode → LLM → MCP tool → mesh → fork.

§6Honest Close

O trabalho de Phase 8.x + Phase 9.x + Phase 10.0 não foi em vão — cada subsystem individual é real. Mas "fully ready" foi vendido baseado em testes isolados, não em uso real. A promessa era integração; o que foi entregue foram peças.

Para chegar a um sistema de fato usável, três caminhos:

  1. Consertar estruturalmente — resolver conflitos de versão OTel, atualizar packages list, corrigir bat, escrever um teste de integração end-to-end. Estimativa: meio dia.
  2. Rollback para estado conhecido-funcional — reverter os 3 commits desta sessão (Tier 5 wiring + dcode entry + .mcp.json fix) e voltar para o estado em edc313e2.
  3. Pausar — voltar amanhã com cabeça fria, ler este mapa antes de mexer.

A lição mais importante: smoke test unitário não é prova de sistema funcionando. Cada vez que eu disse "shipped", eu deveria ter rodado o caminho completo primeiro. Não vou vender mais "fully ready" baseado em testes parciais.
