§ 0 o que foi perguntado

Cinco perguntas, cinco respostas

A pergunta original tinha cinco partes. Nenhuma delas precisou de uma seção própria — cada uma cabe em um parágrafo porque a evidência já está no repositório.

Até onde vai a praticidade de manter forks de interfaces customizadas sobre um protocolo único de dados?
O protocolo é único e nunca bifurcou. São 967 linhas em src/contracts/ — UEID de 4 partes, Pydantic v2 estrito. As superfícies ao redor bifurcaram 8 vezes. O custo do fork não está no contrato; está nas 8 implementações concorrentes que ninguém reconciliou (§2).
Qual o ganho real de escrever um harness próprio sobre LangGraph, em vez de specs de skill por workflow?
Zero, para um usuário só. O ganho do LangGraph é execução durável, checkpointing e branching determinístico — você é o scheduler, o gate human-in-the-loop e o resume. E o achado mais forte: 10 dos 16 nós do grafo são prompts com roupa de Python (14–35 linhas cada). LangGraph brilha exatamente onde está o prompt, que é onde ele não faz diferença.
Harness de terceiro, ou engenharia de dados própria?
Engenharia de dados própria. Nenhum harness de terceiro. Todo framework de agente — LangGraph, Pydantic AI, CrewAI, smolagents, Letta — reimplementa o que o Claude Code já entrega (fan-out via Task, tool use, HIL, sessão). Se o hermes um dia precisar dirigir isso, exponha a CLI como servidor MCP com fastmcp: ~50 linhas, contra os 22 tools do gateway custom dos quais 9 apontam para tools inexistentes.
Quanto falta para completar a aplicação exatamente como planejado, ou quanto se ganha pivotando?
Terminar: ~6–9 pessoa-meses, e não resolveria. O caminho pivotado: ~3 dias para gerar o artefato visual que você pediu. A razão pela qual terminar não resolveria está no §1 — o gate que trava o vault é circular, e código novo não o desfaz.
O que vale customizar, em definitivo?
Uma regra só: onde há invariante, código; onde há julgamento, prompt. Invariante = formato UEID, sole-writer do vault, append-only, rename atômico, idempotência em ueid, thresholds determinísticos, renderização do Gantt. Julgamento = sugerir melhorias, surfaced intentions, score vectors, balance, plan, reflect. Isso decide os 16 nós de uma vez (§5).

Por que isso decide a questão

LangGraph vale por branching determinístico sobre estado compartilhado. O branching dos 10 nós acima é julgamento — o grafo não decide, ele pede pro LLM decidir, e aí o LLM lê um prompt e decide o mesmo que decidiria lendo o mesmo prompt num .md.

Então o grafo é 80% prompt com cadastro no Python. O valor do LangGraph está concentrado nos ~6 nós que são código de verdade — e esses não precisam de grafo: são uma função que lê o vault e devolve um Proposal.

# interfaces/cli/skill_run.py  (~150 LOC)
@app.command(name="skill-run")
def skill_run(name: str, json_out: bool = typer.Option(False, "--json")):
    """Run a skill module by name. No LLM, no graph, no gateway."""
    mod = get_skill(name)              # SKILL_REGISTRY

    payload = {**result.to_dict(), **getattr(result, "metadata", {})}

    else:

    return 0

Bug a corrigir no caminho

Proposal.to_dict() é asdict(self) (proposals.py:61), e asdict só serializa campos declarados. Mas ikigai_daily.py:97 anexa metadata dinamicamente — as sugestões do daily desaparecem no JSON. A linha {**result.to_dict(), **getattr(result, "metadata", {})} acima resolve. Alternativa mais limpa: dar a Proposal um campo metadata: dict = field(default_factory=dict).

A regra que quebra o gate circular

O skill é consumidor, não produtor. Ele lê markdown e arquivos .json e escreve dois arquivos. Não precisa do agent layer, do MCP gateway, do LangGraph nem de LLM. Ele pode rodar hoje, com o vault meio vazio — e a lacuna aparece no Gantt como informação, não como bug.
