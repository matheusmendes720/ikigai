# SPEC-01 — O DOM Unificado

**Date:** 2026-11-01 · **Status:** proposed · **Depends on:** — · **Blocks:** 02, 03
**Origin:** [ADR-037 §3 D2](../../code-docs/adr/ADR-037-data-layer-canonical-turn.md)

---

## Goal

Um **modelo de dados único e compartilhado** (`src/contracts/`) que serve todas as aplicações, com **tipagem forte** e **UID** como chave de artefato — e que qualquer cliente possa projetar em views diferentes sem duplicar dados.

---

## Por que agora

O Vanilla Pivot §2 catalogou **8 bifurcações**. Duas morrem com este spec:

| Fork | Antes | Depois |
|---|---|---|
| **3 — Backends de tarefa** | cli jsonl · taskdog SQLite · solverforge calendar — 3 schemas concorrentes | **1 DOM**, N projeções |
| **5 — Definição de UEID** | 4 partes vs 5 partes | **1 identidade de tipo** (ADR-033 já unificou o regex) |

E o fork **1 — entry_point de skill** (nó do grafo vs callable) deixa de existir quando o transporte é MCP sobre services (SPEC-03).

O problema que este spec resolve **não** é "onde guardar os dados" (isso é a SPEC-02). É: **qual é a forma do dado**. Se o DOM não for definido primeiro, cada consumidor inventa o seu — que é exatamente o que produziu 3 backends de tarefa e 3 UIs para 1 usuário.

---

## Anti-padrão que este spec evita

**O JSONB universal.** A tentação de "um store, um schema, acabou" é `payload jsonb` com-shape-livre. Isso é o oposto de tipagem forte: cada consumidor valida por conta própria, o shape degrada em silêncio, e o índice é impossível.

**O enum que vira string livre.** `kind: str` com valores "kpi", "KPI", "Kpi" aceitos.

**O schema por cliente.** Campo `telegram_message_id`, campo `tui_column` — o DOM vira o espelho de cada interface, e a quarta interface quebra o schema.

---

## Decisões

- **D1 — Espinha + extensões tipadas.** Uma tabela/tabela-Pydantic `Artifact` com os campos comuns (uid, kind, title, body, parent, quarter, status, revision, timestamps), e **um tipo derivado por kind** com os campos específicos tipados. Um DOM só, tipagem forte por kind, sem JSONB universal.

- **D2 — UID = chave primária de todo artefato.** `src.contracts.common.UEID` (a **classe** `UEID(str)`, `src/contracts/common.py:60`). Uma identidade só — não a variante `Annotated[str, StringConstraints]` de `sys_ikigai/entities/ueid.py` (deferida por ADR-033 Alt E).

  > **C7:** o "fork 5 / UEID P0" do Vanilla Pivot §2 está **defasado**. ADR-033 (2026-09-21) já fez `sys_ikigai/entities/ueid.py` **importar** `_UEID_PATTERN` — o regex tem fonte única. O que resta são **duas identidades de tipo**, e o DOM escolhe uma.

- **D3 — 10 kinds, derivados do que existe.** Não são inventados: 6 vêm da árvore real do vault (`vault/ikigai/closing-2026/`: `00-sonho/`, `01-plano-trimestral/`, `02-onda-*/`, `03-revisões-semanais/`, `04-relatórios-diários/`) e 4 (kpi, desc, okr, decisao) são os que o Vanilla Pivot §7 provou necessários para as views.

- **D4 — Grafo é parte do DOM.** Arestas tipadas entre UIDs, com FK real. Não é "efeito colateral" nem tabela separada: o grafo é uma relação de primeira classe entre artefatos, versionada como o resto.

- **D5 — Projeção é responsabilidade do cliente.** O DOM diz *o que é* um KPI (métrica, alvo, atual, unidade, período, direção). **Quem decide** que o Telegram mostra uma barra e a TUI mostra um número é o cliente. Nenhum campo de interface no contrato.

- **D6 — Envelope de escrita explícito.** Toda escrita carrega `expected_revision` (otimista) + `idempotency_key` + `client_id`. Sem isso, "múltiplos clientes" é last-write-wins silencioso.

- **D7 — Busca é parte do contrato.** `SearchQuery` é um tipo do DOM com filtros tipados e **cursor** (não offset) — paginação estável sob escrita concorrente.

- **D8 — Corpos de nota em markdown, não HTML.** O vault é markdown (ADR-037 D4). O DOM guarda o mesmo texto, e o `body_hash` permite reconciliar markdown ↔ store sem diff semântico.

```python
# src/contracts/dom.py
from __future__ import annotations

from datetime import datetime
from decimal import Decimal
from enum import StrEnum
from typing import Any, Literal

from pydantic import BaseModel, ConfigDict, Field

from .common import UEID          # import RELATIVO: dentro de src/contracts/ o repo
                                 # usa relativo (ver task.py:20); dotted-prefix é
                                 # só para crossing de pacote (ver sys_ikigai/entities/ueid.py)

__all__ = [
    "ArtifactKind", "Artifact", "RelationType", "Relation",
    "WriteRequest", "SearchQuery", "SearchResult", "ArtifactRevision",
    "DOMAIN",
]

DOMAIN = "ikig"


class ArtifactKind(StrEnum):
    """The 10 kinds. Derived from the real vault tree + the views that need them."""

    SONHO = "sonho"          # 00-sonho/
    PLANO = "plano"          # 01-plano-trimestral/
    ONDA = "onda"            # 02-onda-<n>/
    FASE = "fase"            # phase rows inside the quarterly plan
    REVISAO = "revisao"      # 03-revisões-semanais/
    NOTA = "nota"            # 04-relatórios-diários/
    KPI = "kpi"
    DESC = "desc"            # decision (DESC)
    OKR = "okr"
    TAREFA = "tarefa"


class Artifact(BaseModel):
    """The spine. Every kind inherits these fields; nothing else is common."""

    model_config = ConfigDict(frozen=True, extra="forbid")

    uid: UEID
    kind: ArtifactKind
    title: str
    body: str | None = None            # markdown for prose kinds
    body_hash: str | None = None       # sha256 of body, for markdown<->store reconciliation
    parent_uid: UEID | None = None
    quarter: str | None = None         # "Q4-2026" — denormalized for the hot index
    status: str | None = None
    revision: int = Field(default=1, ge=1)
    created_at: datetime
    updated_at: datetime
    deleted_at: datetime | None = None  # soft delete: append-only survives
```

## Como um cliente converte KPI/DESC/OKR em UID

O ponto que o owner levantou — *"converter os KPIs, desc, okrs em uid para artefatos em diferentes views da timeline"* — é uma **função de mapeamento**, e ela mora no **cliente**, não no DOM:

```
KPI "taxa de conclusão" / "2026-Q4"
        │
        ├─► Telegram view  (barra horizontal, número grande)
        └─► TUI view       (coluna do kanban)
                │
                └── as DUAS views apontam para o MESMO uid
```

O DOM dá `uid` + os campos. O cliente decide a forma. **Um artefato, N views, zero duplicação** — que é o oposto dos 3 backends de tarefa.

O UEID carrega o `kind` no primeiro segmento (namespace). O mapeamento canônico é:

| Fonte no vault | Kind | Namespace sugerido |
|---|---|---|
| `00-sonho/*.md` | `sonho` | `snh` |
| `01-plano-trimestral/*.md` | `plano` | `pln` |
| `02-onda-<n>/*.md` | `onda` | `ond` |
| tabela de fases do plano | `fase` | `fse` |
| `03-revisões-semanais/YYYY-Www.md` | `revisao` | `rev` |
| `04-relatórios-diários/YYYY-MM-DD.md` | `nota` | `not` |
| KPI | `kpi` | `kpi` |
| decisão | `desc` | `dec` |
| OKR | `okr` | `okr` |
| tarefa | `tarefa` | `tsk` |

## Fora de escopo

- O **store** (tabelas, índices, RLS, vector) — é a SPEC-02.
- A **sync** vault markdown ↔ store — SPEC-02/03.
- O **cliente Telegram** e a **timeline** — depois.
- `update`/`delete`/`done` no **mesh** (v1.2+, ADR-013).
- Mexer na **identidade de tipo** do UEID (ADR-033 Alt E — deferido; o DOM escolhe uma das duas e segue).

## Self-review

D1–D8 cobertas. Task 1.5 é a invariante load-bearing (o drift net do repo protege invariante — ADR-013). O enum de kinds é pequeno e justificado (D3). O contrato tem ~6 modelos, não 30: os kinds compartilham a espinha, e só os que precisam de tipagem própria a têm.

**Risco:** a espinha `Artifact` não tem lugar para "campos de cliente" — e é exatamente isso que D5 proíbe. Se um dia um cliente precisar de um campo próprio, ele vai para o `meta: dict` do kind específico, **não** para a espinha.
