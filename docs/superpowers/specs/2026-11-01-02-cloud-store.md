# SPEC-02 — O Store Cloud

**Date:** 2026-11-01 · **Status:** proposed · **Depends on:** SPEC-01 · **Blocks:** 03
**Origin:** [ADR-037 §3 D3, D4, D5](../../../code-docs/adr/ADR-037-data-layer-canonical-turn.md)

---

## Goal

Um **único Postgres serverless** que hospeda o vault estruturado: versionado, com **busca rápida por índices estruturados**, servindo **vector**, **graph** e **embeddings** — e com escrita concorrente segura entre múltiplos clientes e dispositivos.

---

## Por que agora

O Vault Pivot §1 mediu o problema central: **39% verde, 7 semanas de silêncio no vault, e todo caminho automatizado lendo a árvore vazia** porque o vault é markdown sem índice.

Markdown é ótimo para **prosa** e péssimo para **consulta**. Os 6 tipos de leitura que o owner precisa (nota do dia, KPI do trimestre, OKR da onda, decisão, dependência, embedding) hoje exigiriam `grep` sobre arquivos — o que produziu a classe de bug "teste-tautologia que passa para sempre" (SPEC-01 do Vanilla Pivot §Anti-padrão).

O store resolve isso com **índices reais** e **transações**, não com mais leitura de arquivo.

---

## Anti-padrão que este spec evita

**"Supabase já está decidido."** O owner disse *"pode ser supabase"* — é **candidata**, não decisão. A diferença importa porque a escolha define custo,_ops e a superfície de segurança (RLS vs auth próprio). Mas **o schema é Postgres puro**, então a escolha é reversível sem tocar contrato.

**O Chroma separado.** O repo já tem `vibe_ops.db` com "coleção criada, 0 embeddings" (§1 do Vault Pivot). Um segundo banco de embeddings é um segundo backup, uma segunda consistência, uma segunda política de acesso. **pgvector no mesmo Postgres** resolve numa transação.

**O lock distribuído.** Para "paralelismo e multi-threading entre clientes", a tentação é lock/fila. A resposta é `revision` otimista + transação: **conflito explícito (409) em vez de espera**.

**O `ON CONFLICT DO UPDATE` silencioso.** UPSERT que sobrescreve a última escrita destrói a versão de um cliente. Com `expected_revision`, é rejeitado.

---

## Decisões

- **D1 — Postgres serverless, um store.** Tabelas, índices, vector, arestas, revisões e RLS no **mesmo** banco. Uma transação, um backup, uma política de acesso.

- **D2 — A tabela `artifacts` é a espinha; extensões por kind.** `artifacts` guarda o comum (D1 da SPEC-01); tabelas `artifact_kpi`, `artifact_okr`, `artifact_decs`, … guardam o específico com colunas **tipadas** + `CHECK`. Nenhum `jsonb` universal.

- **D3 — Grafo em tabela de arestas com FK real.** `artifact_relations(src_uid, dst_uid, rel, ...)` com FK para `artifacts(uid)` em ambas as pontas e índices nas duas direções. Grafo navegável com integridade, não com JSON aninhado.

- **D4 — Versionamento append-only em duas tabelas.** `artifacts.revision` (otimista, para conflito) + `artifact_revisions` (histórico append-only, imutável). `deleted_at` para soft delete — **nunca `DELETE` físico**.

- **D5 — Concorrência otimista.** `UPDATE ... WHERE uid = $1 AND revision = $2` → 0 linhas afetadas = **conflito (409)**. `idempotency_key` com índice único impede reenvio duplicado. **Sem lock distribuído, sem espera, sem last-write-wins.**

- **D6 — RLS por `client_id`.** O cliente é 1 usuário com N dispositivos. O claim `client_id` vem do JWT da service; RLS filtra por ele. Não por `auth.uid()` (ver C5).

- **D7 — Embeddings em coluna `vector` com dimensão fixa.** `EMBEDDING_DIM` é constante ratificada junto com o fornecedor (R1). Mudar a dimensão = **nova coluna + backfill**, porque o índice HNSW exige dimensão fixa.

- **D8 — Migrations versionadas e aditivas.** Arquivos SQL numerados em `src/contracts/migrations/`. Sem `DROP COLUMN` em produção sem etapa de depreciação. Um único runner, um único lock de migration (advisory lock do Postgres).

- **D9 — Sync bidirecional com direção explícita.** Markdown → store (prosa); store → markdown (prosa editada no cliente). **Em campo estruturado, o store vence.** É isso que mata o bug das 2 árvores.
- **D10 — Fornecedor: Supabase (ratificado 2026-11-01).** pgvector + RLS + Realtime + Edge Functions sem operação própria. O schema é Postgres puro, então trocar de fornecedor depois é 3 linhas de conexão — **não** é uma decisão que trava arquitetura.
- **D11 — Postgres de teste no CI via testcontainers.** Os testes de store (concorrência, RLS, drift contrato↔SQL) rodam em **todo PR**. Sem isso, a Task 2.5 seria a única verificação em CI — mais fraco do que a spec pede.

## Contrato — o schema

```sql
-- 0001_init.sql
create schema if not exists ikig;

-- espinha ------------------------------------------------------------------
create table ikig.artifacts (
    uid          text primary key,
    kind         text        not null,
    title        text        not null,
    body         text,
    body_hash    text,
    parent_uid   text        references ikig.artifacts(uid),
    quarter      text,
    status       text,
    revision     integer     not null default 1 check (revision >= 1),
    created_at   timestamptz not null default now(),
    updated_at   timestamptz not null default now(),
    deleted_at   timestamptz,
    -- o UID segue _UEID_PATTERN (ADR-014/033): a constraint é gerada do contrato,
    -- nunca copiada à mão
    constraint artifacts_uid_format check (uid ~ '^(?:[a-z]{2,8}:[a-z0-9][a-z0-9_-]{0,62}[a-z0-9]:[a-f0-9]{4,8}:[a-f0-9]{4,8})$'),
    constraint artifacts_kind_known check (kind in ('sonho','plano','onda','fase','revisao','nota','kpi','desc','okr','tarefa'))
);

-- extensões tipadas por kind ------------------------------------------------
create table ikig.artifact_kpi (
    uid        text primary key references ikig.artifacts(uid) on delete cascade,
    metric     text      not null,
    target     numeric,
    actual     numeric,
    unit       text,
    period     text      not null,
    direction  text      not null default 'up' check (direction in ('up','down','flat'))
);

create table ikig.artifact_okr (
    uid          text primary key references ikig.artifacts(uid) on delete cascade,
    objective    text      not null,
    key_result   text      not null,
    kr_target    numeric,
    kr_actual    numeric,
    kr_progress  numeric   check (kr_progress is null or (kr_progress >= 0 and kr_progress <= 1))
);

create table ikig.artifact_decs (
    uid        text primary key references ikig.artifacts(uid) on delete cascade,
    decision   text      not null,
    rationale  text,
    decider    text,
    outcome    text
);

-- grafo ---------------------------------------------------------------------
create table ikig.artifact_relations (
    src_uid   text not null references ikig.artifacts(uid),
    dst_uid   text not null references ikig.artifacts(uid),
    rel       text not null,
    weight    double precision,
    meta      jsonb not null default '{}'::jsonb,
    created_at timestamptz not null default now(),
    primary key (src_uid, dst_uid, rel),
    constraint relations_no_self_loop check (src_uid <> dst_uid)
);

-- versionamento --------------------------------------------------------------
create table ikig.artifact_revisions (
    uid        text        not null,
    revision   integer     not null,
    snapshot   jsonb       not null,
    author     text,
    client_id  text        not null,
    created_at timestamptz not null default now(),
    primary key (uid, revision)
);

create table ikig.idempotency_keys (
    key        text        primary key,
    client_id  text        not null,
    uid        text        not null,
    created_at timestamptz not null default now()
);
```

create index ix_artifacts_kind_quarter on ikig.artifacts (kind, quarter) where deleted_at is null;

update ikig.artifacts

## R1 — Fornecedor ratificado: **Supabase** (2026-11-01)

| Opção | pgvector | RLS | Realtime | Edge Functions | Custo | Operação |
|---|---|---|---|---|---|---|
| **Supabase** (recomendado) | ✅ nativo | ✅ nativo | ✅ | ✅ | free tier generoso | zero |
| Neon (Postgres gerenciado) | ✅ (extensão) | ❌ (RLS próprio) | ❌ | ❌ | baixo | médio |
| VPS + Postgres + pgvector | ✅ | ❌ (implementar) | ❌ | ❌ | mínimo | **alta** |

**Recomendação: Supabase.** Entrega as 4 capacidades que a decisão exige (multi-client + RLS + realtime + vector) sem operação própria. O schema é Postgres puro — trocar de fornecedor muda **3 linhas de conexão** e nenhum contrato.

**DECIDIDO pelo owner em 2026-11-01: Supabase.** A ratificação confirma a recomendação — o schema, os contratos e as tasks 2.2–2.5 **não mudam**. Trocar de fornecedor depois continua sendo 3 linhas de conexão (SPEC-03 T3.1), porque o schema é Postgres puro.

## R2 — Como o store substitui o `grep`

| Pergunta | Hoje (markdown) | Com o store |
|---|---|---|
| "Qual foi a nota de 2026-10-30?" | `find vault/ -name "2026-10-30.md"` → arquivo talvez não exista | `select ... where kind='nota' and created_at::date = '2026-10-30'` |
| "KPIs do Q4 com alvo estourado" | impossível | índice em `(quarter, kind)` + `actual > target` |
| "O que bloqueia a Onda 2?" | impossível | `artifact_relations` com `rel='blocks'` |
| "Nota que menciona embeddings" | `grep` (sem embedding) | busca semântica por `vector_cosine_ops` |

**É aqui que morre o bug das 2 árvores** (ADR-037 D4): o dado estruturado tem **uma** fonte, indexada.

## Self-review

D1–D9 cobertas. R1 é a única variável aberta e está isolada nas Tasks 2.0/2.1 — **o resto da spec é executável com qualquer fornecedor Postgres**. Task 2.5 é a invariante load-bearing (o repo protege invariante com drift test — ADR-013 §"Persistent enforcement"). Task 2.6 é o teste que prova o requisito "paralelismo e multi-threading" sem vender lock distribuído.

**Risco:** `numeric` para `target`/`actual` mapeia para `Decimal` no Pydantic (SPEC-01) — conversión implícita de float é onde KPI perde precisão. O contrato usa `Decimal` explicitamente para fechar isso.
