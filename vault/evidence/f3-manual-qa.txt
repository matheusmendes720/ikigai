Additional Findings (out of original scope, but worth noting)
================================================================================

1. Index count mismatch (DOC): Plan §Must Have says "6 indexes covering: period, sonho_id, parent_period, verdict, policy_recommendation, vault_hash, updated_at" — but that's 7 items. Implementation has 7 indexes (matching the items, not the stated count). This is a doc inconsistency, not a bug.

2. Vault_hash idempotency deviation (BEHAVIOR): Plan §Must Have says "Idempotent sync via vault_hash (sha256 canonical JSON, 16 chars)". However, the actual implementation in `_fetch_existing()` uses `id = ? OR vault_hash = ?` but `_fetch_existing` is only called AFTER the id check, so re-syncing the same id always skips regardless of vault_hash change. The integration test `test_update_existing_report` (lines 235-276) explicitly documents this: "Modifying a report (same id, different content) is NOT auto-propagated." This is a functional deviation from the plan's stated intent. The integration test acknowledges it but doesn't flag it as a failure. Operationally, this means: edits to existing period reports in the vault are NOT propagated to the DB on re-sync. Users must change the file's `id` field to trigger an update.

3. Re-application: Running tests/integration/test_period_sync.py::test_update_existing_report shows that after modifying verdict from ACTIVE to PIVOTED in the same file id, the DB retains the original ACTIVE verdict (asserted at line 275-276 of test file). This is a silent data-loss risk for users who edit their vault files.
